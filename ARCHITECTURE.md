# Архітектура PDM (Personal Data Memory) SDK

Цей документ надає детальний і вичерпний опис архітектури, математичного апарату, внутрішньої структури компонентів та потоків даних у **PDM (Personal Data Memory) SDK**. 

---

## 1. Концептуальний огляд

Стандартні підходи до побудови RAG (Retrieval-Augmented Generation) систем зазвичай покладаються на векторні бази даних, які шукають інформацію на основі семантичної близькості слів (косинусної подібності ембедингів). Такий підхід має значні недоліки: він дорогий, обчислювально складний і знаходить інформацію, яка відповідає **словам, а не значенню чи важливості**.

**PDM вирішує цю проблему за допомогою динамічного моделювання людської пам'яті (Pressure-Driven Memory).** Замість сирого тексту PDM зберігає стислі факти у вигляді сигнатур із асоційованими метаданими, тегами та динамічним показником «тиску» (pressure).

### Ключові принципи PDM:
1. **Тиск пам'яті (Memory Pressure):** Кожен спогад має початкову величину тиску ($p\_magnitude$). Спогади, які використовуються частіше, підсилюються, підвищуючи свій тиск. Спогади, що не використовуються, з часом затухають (decay).
2. **Пошук із регулюванням порогу (Threshold-Adjustment Search - TAS):** Замість простого пошуку найближчих векторів, PDM динамічно знижує поріг тиску для пошуку в умовах невизначеності запиту, а потім ранжує спогади за допомогою «резонансного скорингу» (coupling score), який враховує перетин тегів, домен, режим контексту та поточний тиск.
3. **Обчислення згасання «на льоту» (On-Read Decay):** Згасання тиску обчислюється в момент виконання запиту. Це дозволяє уникнути необхідності в постійних фонових планувальниках завдань (таких як Celery або Redis Queue), забезпечуючи роботу системи без зайвої інфраструктури.
4. **Коефіцієнт валідації (Validation Coefficient - $V$):** Зворотний зв'язок щодо корисності спогаду згладжується за методом Лапласа, що дозволяє спогадам, які довели свою корисність у передбаченнях LLM, затухати повільніше.

### Опис ключових модулів:

1. **`pdm_memory.Memory` (Точка входу):** Фасадний клас, з яким безпосередньо взаємодіє розробник. Він інкапсулює роботу зі сховищем, двигуном пошуку, синхронізацією та імпортом даних.
2. **`pdm_memory.storage.base.BaseStorage`:** Абстрактний інтерфейс, який описує контракт для будь-якого сховища PDM-сигнатур. Завдяки цьому Memory не знає деталей реалізації драйверів.
3. **`pdm_memory.storage.sqlite_driver.SQLiteDriver`:** Локальний thread-safe драйвер, що працює з SQLite. Забезпечує збереження даних у файл `.db` та підтримує режим максимальної приватності (зберігання лише хешів SHA-256 замість сирого тексту).
4. **`pdm_memory.storage.cloud_driver.CloudDriver`:** HTTP-драйвер до **AZUS Companion API** (`https://api.azus.ai` за замовчуванням). Покриває той самий `BaseStorage`-контракт, що SQLite/Postgres: single-row `ingest` / get / patch, soft-delete (`is_deleted`) і hard `DELETE`, keyset-list (`GET /pdm/signatures`), batch create/get/update (chunk 100), lookup за `idempotency_key` і content-hash (`by-hash`), `ping`. JWT з автоматичним refresh на 401. Batch-маршрути fail-fast (немає silent sequential fallback), непідтримувані PATCH-поля (напр. client-side `effective_spike`) відсікаються перед запитом.
5. **`pdm_memory.core.retrieval.RetrievalEngine`:** Реалізація алгоритму **TAS (Threshold-Adjustment Search)**. Працює виключно в оперативній пам'яті з масивами об'єктів `SignatureRecord`, що робить його незалежним від конкретної бази даних.
6. **`pdm_memory.core.math`:** Набір чистих математичних функцій (без залежностей від Django, SQLAlchemy чи Celery), які обчислюють згасання, коефіцієнт валідації, тиск та часову геометрію.
7. **`pdm_memory.sync.MemorySync`:** Утиліта для двосторонньої синхронізації між локальною базою даних SQLite та хмарою AZUS Cloud з автоматичним вирішенням конфліктів на основі величини тиску.
8. **`pdm_memory.ingest`:** Модуль для пакетного завантаження даних із CSV чи списків словників з можливістю автоматичного стиснення фактів та генерації тегів за допомогою мовних моделей.

## 3. Математичний апарат PDM

Математичні формули є ядром PDM SDK і реалізовані у модулі `pdm_memory/core/math.py`.

### 3.1. Ефективний сплеск тиску (Effective Spike)

При додаванні спогаду обчислюється його початковий ефективний сплеск тиску ($effective\_spike$). Він відображає початкову значущість спогаду з урахуванням часу його життя та привілею фази:

$$\text{effective\_spike} = \min\left(100, \max\left(0, P_{\text{magnitude}} \times \frac{t_{\text{persistence}}}{30} \times \text{phase\_privilege}\right)\right)$$

Де:
*   $P_{\text{magnitude}}$ — базовий тиск спогаду (0–100).
*   $t_{\text{persistence}}$ — період гарантованого збереження спогаду в днях (протягом якого він не затухає).
*   $\text{phase\_privilege}$ — коефіцієнт вкладеності або пріоритету контексту (зазвичай 1.0).

---

### 3.2. Експоненційне згасання (Exponential Decay Factor)

Якщо спогад не запитується, його динамічний тиск зменшується. Коефіцієнт згасання ($decay\_factor$) обчислюється на основі часу, що минув з моменту останнього зчитування:

$$\text{decay\_factor} = 1 - e^{-\lambda \times t}$$

Де $\lambda$ — константа швидкості згасання, що залежить від періоду напіврозпаду для конкретного домену знань:

$$\lambda = \frac{\ln(2)}{T_{1/2}}$$

$t$ — кількість днів (включаючи дробову частину), що минули з моменту останнього підсилення або створення спогаду.

#### Періоди напіврозпаду за доменами ($T_{1/2}$):
PDM класифікує знання на різні домени, кожен з яких має свій життєвий цикл:

| Домен знань (`domain`) | Період напіврозпаду ($T_{1/2}$) | Опис / Приклад |
| :--- | :--- | :--- |
| `market_signal` | 1.0 день | Ринкові дані, новини швидкого реагування |
| `warning` | 3.0 дні | Попередження про ризики або помилки |
| `reminder` | 7.0 днів | Нагадування про задачі, дедлайни |
| `pattern` | 14.0 днів | Аналогії, історичні закономірності |
| `insight` | 30.0 днів | Загальні інсайти, висновки |
| `structural` | 90.0 днів | Структурні моделі, архітектурні патерни |
| `core_fact` | 365.0 днів | Загальні фундаментальні правила, факти |

---

### 3.3. Коефіцієнт валідації (Validation Coefficient)

Показник надійності спогаду $V$ базується на історії його успішного застосування (корисність передбачень у минулому). Для уникнення ділення на нуль та пом'якшення оцінки на малих вибірках використовується **згладжування Лапласа (Laplace Smoothing)**:

$$V = \frac{\text{correct} + 1}{\text{total} + 2}$$

Де:
*   $\text{correct}$ — кількість випадків, коли спогад допоміг надати правильну відповідь.
*   $\text{total}$ — загальна кількість використань спогаду для валідації.
*   Діапазон значення $V$: від $0.333333$ (якщо історія відсутня) до $1.0$ (при великій кількості виключно успішних застосувань).

---

### 3.4. Вага наміру (Intent Weight)

Обчислює семантичний збіг між тегами сигнатури та словами в запиті користувача. Базова вага становить $0.8$, а решта $0.2$ нараховується пропорційно перетину тегів із токенами запиту:

$$\text{intent\_weight} = 0.8 + 0.2 \times \frac{\text{matches}}{\text{len}(\text{intent\_tags})}$$

Де $\text{matches}$ — кількість тегів спогаду, які містяться в нормалізованому текстовому запиті. Якщо запит відсутній, значення за замовчуванням дорівнює $1.0$.

---

### 3.5. Розрахунок ефективного тиску ($P_{effective}$)

Це підсумкове значення тиску спогаду, яке розраховується динамічно під час кожного пошуку:

$$P_{\text{effective}} = P_{\text{magnitude}} \times V \times (1 - \text{decay\_factor}) \times \text{intent\_weight} \times \text{quality} \times \text{comparator}$$

Де:
*   $P_{\text{magnitude}}$ — поточний збережений тиск у БД.
*   $V$ — коефіцієнт валідації.
*   $\text{decay\_factor}$ — експоненційне згасання з моменту останнього зчитування.
*   $\text{intent\_weight}$ — вага відповідності запиту.
*   $\text{quality}$ — коефіцієнт якості сигналу (за замовчуванням $0.80$).
*   $\text{comparator}$ — додатковий проксі-множник для тонкого калібрування (за замовчуванням $1.0$).

---

### 3.6. Покрокове інкрементне згасання (Incremental Decay)

Оскільки PDM не використовує зовнішніх планувальників, при кожному виклику `recall()` або `decay()` виконується інкрементне згасання збереженого значення тиску у БД, якщо минув період гарантованого збереження $t_{\text{persistence}}$:

$$\text{new\_p} = \begin{cases} 
P_{\text{magnitude}} \times \text{decay\_rate}^{(\text{days\_elapsed} - t_{\text{persistence}})}, & \text{якщо } \text{days\_elapsed} > t_{\text{persistence}} \\
P_{\text{magnitude}}, & \text{якщо } \text{days\_elapsed} \le t_{\text{persistence}} 
\end{cases}$$

Де:
*   $\text{days\_elapsed}$ — час у днях з моменту створення спогаду.
*   $\text{decay\_rate}$ — мультиплікатор згасання тиску за день після закінчення гарантованого періоду (за замовчуванням $0.9$, тобто втрата 10% тиску щодня).

Якщо в результаті інкрементного згасання тиск спогаду падає нижче критичного порогу **`DECAY_DELETE_THRESHOLD` (30.0)**, такий спогад остаточно видаляється зі сховища як неактуальний шум.

---

### 3.7. Часова геометрія PDM-T (Temporal Deformation)

Для спогадів, які мають чіткий дедлайн (наприклад, завдання або нагадування), застосовується модель часової деформації **PDM-T**. Вона симулює зростання тривожності (тиску) наближенням до дедлайну.

#### До настання дедлайну ($T_{\text{remaining\_days}} > 0$):

1.  **Деформація кривизни ($C_T$):**
    $$C_T = \min\left(5.0, c_{\text{base}} \times \left(1 + \frac{\text{persist}}{T_{\text{remaining}}}\right)\right)$$
2.  **Товщина мембрани ($S_T$):**
    $$S_T = \max\left(0.01, \frac{s_{\text{base}}}{1 + \text{urgency\_rate} \times \left(1 - \frac{T_{\text{remaining}}}{\text{persist}}\right)}\right)$$
3.  **Деформований тиск ($P_T$):**
    $$P_T = \min\left(10.0, p_{\text{base}} \times \text{urgency\_rate}^{\frac{1}{T_{\text{remaining}}}}\right)$$
4.  **Енергетична емісія дедлайну ($E_T$):**
    $$\text{raw\_e\_t} = C_T \times \frac{1}{S_T} \times P_T$$
    $$E_T = \min\left(1.0, \max\left(0.0, \frac{\text{raw\_e\_t}}{\text{raw\_e\_t} + 10.0}\right)\right)$$
    
Якщо $E_T > 0.75$, спогад набуває статусу **`URGENT`** (терміновий).

#### Після дедлайну ($T_{\text{remaining\_days}} \le 0$):
Енергія дедлайну скидається до нуля ($E_T = 0$), а вага спогаду починає швидко згасати із кожним днем протермінування:

$$\text{temporal\_weight}_{\text{new}} = \text{temporal\_weight} \times (1 - \text{decay\_rate})^{\text{days\_past}}$$

## 4. Потоки даних та життєвий цикл спогаду

### 4.1. Збереження спогаду (`Memory.save`)

Коли додаток ініціює збереження інформації через SDK:

```
[Сирий текст факту] + [Теги / Джерело / Дедлайн]
                     │
                     ▼
             Memory.save()
                     │
                     ▼
 1. Валідація тексту (обрізка до 500 символів)
 2. Визначення домену знань (на основі тегів)
 3. Обчислення початкового ефективного сплеску (effective_spike)
 4. Створення об'єкта SignatureRecord
                     │
                     ▼
         BaseStorage.save(sig)
                     │
         ┌───────────┴───────────┐
         ▼                       ▼
   [SQLiteDriver]          [CloudDriver]
   - Запис у локальний     - POST /api/v1/pdm/ingest
     файл бази даних       - або ingest/batch (save_many)
                           - dedupe: GET …/by-hash
                           - idempotency: key lookup / ingest
```

На recall storage спочатку тягне кандидатів через `list` (на cloud — `GET /pdm/signatures` без side-effect `retrieve`), далі TAS працює locally in-process як на SQLite.

---

### 4.2. Пошук та вилучення спогадів (`Memory.recall`)

Процес пошуку реалізовано як трифазову процедуру Threshold-Adjustment Search (TAS):

```
       Клієнт викликає Memory.recall(query, search_cost)
                               │
                               ▼
            1. Зчитування кандидатів із сховища
            (лише ті, що мають P_magnitude >= min_pressure)
                               │
                               ▼
        2. Інкрементне згасання кожного кандидата у пам'яті
                               │
                               ▼
        3. Фаза 1 TAS: Зниження порогу тиску (Threshold Lowering)
           theta_eff = base_threshold * (1 - alpha * search_cost)
                               │
                               ▼
        4. Відсікання кандидатів із P_effective < theta_eff
                               │
                               ▼
        5. Фаза 2 TAS: Семантичне узгодження (Impedance Matching)
           Розрахунок coupling_score для кожного кандидата
                               │
                               ▼
        6. Ранжування за формулою: coupling_score * P_effective
                               │
                               ▼
        7. Фаза 3 TAS: Автоматичне підсилення (Reinforcement)
           Для відібраних спогадів викликається:
           new_P = P + REINF_BASE * (1 + log(1 + count)) * coupling_score
                               │
                               ▼
           Пакетний запис оновлених значень P_magnitude в базу даних
                               │
                               ▼
                  Повернення List[MemoryHit]
```

---

### 4.3. Автоматичний імпорт (`Memory.ingest`)

Модуль `pdm_memory.ingest` призначений для міграції застарілих даних (legacy data) у формат PDM. Він може працювати у двох режимах:

#### Режим 1: Прямий імпорт
Використовує евристичні правила для автоматичного мапінгу колонок CSV або ключів словника (наприклад, перейменування `importance` -> `p_magnitude`, `labels` -> `intent_tags`). Якщо теги не вказано, вони автоматично генеруються шляхом вилучення іменників та значущих слів із тексту.

#### Режим 2: Синтез сигнатур через LLM
Якщо в метод передано екземпляр LLM-клієнта (`openai_client` або `anthropic_client`), то для кожного рядка викликається модель `gpt-4o-mini` або `claude-3-haiku`, яка виконує наступну роботу за спеціальним промптом:
1.  Стискає сирий текст у факт довжиною до 500 символів без зайвого шуму.
2.  Визначає від 3 до 5 релевантних пошукових тегів.
3.  Рекомендує рівень первинної важливості $p\_magnitude$ (від 0 до 100).

---

### 4.4. Двостороння синхронізація (`MemorySync.sync`)

Забезпечує консистентність даних між локальною SQLite базою користувача та AZUS Cloud.

#### Вирішення конфліктів:
При синхронізації однакових сигнатур (з однаковим UUID) виникає конфлікт версій. **Стратегія розв'язання конфліктів у PDM:**
*   Перемагає запис, який має **вищий показник тиску ($p\_magnitude$)**. Це гарантує, що найважливіша або найсвіжіша версія факту буде збережена.
*   Якщо тиск однаковий, перемагає запис, створений пізніше.

---

## 5. Структура Даних та Схема БД (SQLite)

Локальний SQLite драйвер автоматично створює таблиці та індекси при першому зверненні. Схема оптимізована для швидкого пошуку сигнатур конкретного користувача та фільтрації за категоріями (шухлядами / drawers).

### 5.1. Таблиця `pdm_signatures`

Містить повну інформацію про кожен окремий спогад:

| Назва колонки | Тип даних | Опис |
| :--- | :--- | :--- |

#### Індекси:
1.  `idx_pdm_user_pressure` на полях `(user, p_magnitude DESC)`: оптимізує вибірку найважливіших спогадів користувача при початковому скануванні в `recall()`.
2.  `idx_pdm_user_drawer` на полях `(user, drawer_domain)`: прискорює пошук спогадів у розрізі окремої категорії.

### 5.2. Таблиця `pdm_drawers`

Зберігає інформацію про розділи/категорії пам'яті:

*   `domain` (TEXT): Назва категорії (шухляди).
*   `user` (TEXT): Власник категорії.
*   `description` (TEXT): Короткий опис призначення категорії.
*   **Первинний ключ (PK):** `(domain, user)`

## 6. Інтеграції з LLM та Клієнтські Адаптери

Для безшовної інтеграції PDM у цикли генерації текстів SDK надає обгортки (adapters) для офіційних клієнтів OpenAI та Anthropic (`wrap_openai` та `wrap_anthropic`).

### Механізм автоматичного циклу пам'яті:

```
                  Клієнт викликає: client.chat("Який формат мені обрати?")
                                             │
                                             ▼
                 1. Автоматичний recall() з текстом запиту користувача
                                             │
                                             ▼
           2. Виклик ContextWindowManager для фільтрації спогадів за токенами
                                             │
                                             ▼
         3. Форматування спогадів у системний блок та ін'єкція у системний промпт
                                             │
                                             ▼
                        4. Відправка запиту до хмарного API LLM
                                             │
                                             ▼
                         5. Отримання відповіді від мовної моделі
                                             │
                                             ▼
          6. Автоматичне збереження запиту користувача та відповіді LLM у базу PDM
             (з низьким початковим тиском: 40 для юзера, 35 для асистента)
                                             │
                                             ▼
                    Повернення відповіді користувачу в додаток
```

#### Контроль контекстного вікна (`ContextWindowManager`):
*   Адаптер отримує обмеження на токени пам'яті (за замовчуванням 1500 токенів).
*   Якщо сумарний обсяг знайдених спогадів перевищує ліміт, `ContextWindowManager` починає відкидати спогади з найменшим значенням ефективного тиску ($P_{\text{effective}}$), поки обсяг не впишеться в бюджет.
*   Для точного підрахунку токенів використовується бібліотека `tiktoken` (кодування моделі, наприклад `cl100k_base`). Якщо бібліотека відсутня в системі, застосовується наближене обчислення за формулою: $\text{tokens} = \frac{\text{len}(\text{text})}{4}$.

## 7. Інструменти розробника та CLI

SDK містить консольну утиліту `pdm-cli` для діагностики, перевірки та обслуговування баз даних пам'яті.

### 7.1. Звіт про прозорість (`Memory.explain`)
Метод дозволяє розробникам зрозуміти, чому саме конкретний спогад піднявся у видачі або який у нього рівень згасання. Він повертає об'єкт `ExplainReport`, що рендерить структуровану таблицю:

```
╔══════════════════════════════════════════════════════
║  PDM Memory Explain Report
╠══════════════════════════════════════════════════════
║  ID:              abc12345-...
║  Fact:            User prefers metric units and short answers
║  Tags:            units, formatting, preferences
╠──────────────────────────────────────────────────────
║  Pressure Components:
║    p_magnitude:    80.00
║    V coefficient:  0.8333  (4 retrievals)
║    Decay factor:   0.0231  (1.0d since retrieved, T½=30d)
║    Intent weight:  1.0000
║    Quality:        0.80
║    ─────────────────────────────
║    P_effective:    55.28
╠──────────────────────────────────────────────────────
║  Resonance (TAS coupling):
║    coupling_score:     0.8750
║    tag_overlap:        1.0000
║    domain_match:       1.0000
║    regime_match:       1.0000
║    pressure_proximity: 0.8000
╚══════════════════════════════════════════════════════
```

### 7.2. CLI команди:
*   `pdm-cli list-memories --store <path>`: виводить список усіх спогадів із зазначенням тиску, тегів та тексту.
*   `pdm-cli explain <id> --store <path> --query "<text>"`: показує математичний звіт та зв'язок для конкретного запиту.
*   `pdm-cli decay --store <path> [--dry-run]`: примусово запускає очистку бази від застарілих спогадів із тиском нижче 30.0.
*   `pdm-cli stats --store <path>`: виводить агреговану статистику по шухлядах (drawers), середньому, мінімальному та максимальному тиску в системі.
*   `pdm-cli sync --store <path> --token <jwt> --direction <push/pull/bidirectional>`: запускає синхронізацію з AZUS Cloud через термінал.
